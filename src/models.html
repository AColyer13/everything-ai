The one rule: memory decides everything

A model's weights must sit in fast memory while it runs. Rough sizing: file size in GB is about parameters (in billions) × bytes per weight. At 16-bit that is 2 bytes, at 8-bit 1 byte, at 4-bit about 0.5 byte. Add room for the KV cache (the model's working memory of the conversation), which grows with context length.

Two numbers matter on any machine: capacity (can the model fit at all) and bandwidth (how fast the chip can read it, which sets tokens per second). This is why a 512 GB machine can load a huge model yet generate slowly, while a 16 GB GPU is fast but limited to small ones.

NVIDIA in the enterprise: how cloud models run

Cloud models such as Claude, GPT and Gemini are too large for any one chip, so providers run them across racks of data-center accelerators. NVIDIA sells most of that hardware.

LayerWhat it isRole
Data-center GPUsHopper (H100, H200) and Blackwell (B200, B300) with HBM, very fast stacked memoryTrain and serve large models. Memory per GPU is roughly 80 to 288 GB depending on generation.
HGX / DGX servers8 GPUs linked by NVLink in one boxThe standard building block. A model can be split across the 8 GPUs.
Rack-scale systemsGB200 / GB300 NVL72: dozens of GPUs and Grace CPUs wired as one big acceleratorServe the largest models and huge numbers of users at once.
NetworkingNVLink inside a server or rack, InfiniBand or Ethernet between racksMoves data between chips so the model behaves as one unit.
SoftwareCUDA, TensorRT-LLM, Triton, NIM microservicesThe reason most AI software targets NVIDIA first.

Clouds sell this as an API (you pay per token) or as rented GPUs (you pay per hour, for example for the 8×H100 runs on the LLM page). Enterprises also buy the hardware for their own data centers when data cannot leave the building.

Parameter size: what the number means

A parameter is one learned number in the network. More parameters usually means more knowledge and better reasoning, at the cost of memory and speed.

Dense versus mixture of experts (MoE)

A dense model uses all its parameters for every token. A mixture-of-experts model holds many specialist sub-networks and activates only a few per token. A "125B" MoE model that activates about 6B parameters per token needs memory for all 125B but reads only about 6B per token, so it generates much faster than a dense 125B model. That trick is what makes huge models usable on desktop machines.

Quantization

Quantization stores weights with fewer bits (8, 4, or even 2). It shrinks the file and speeds up generation with some quality loss; 4-bit is the usual sweet spot. QAT (quantization-aware training) means the model was trained with the low precision in mind, so it loses less quality than compressing afterward.

Context length

The context window is how much text the model can consider at once (128K tokens is roughly a 300-page book). Longer context costs memory for the KV cache and slows prompt processing, so a model that "supports" 256K may not fit 256K on your hardware.

What each can run (rules of thumb)

  • DGX Spark (128 GB): models up to about 100 to 120B parameters at 4-bit, best when they are MoE so generation stays fast.
  • Mac Studio (512 GB): 4-bit models up to roughly 400B+ parameters, or a mid-size model at high precision with a very long context.
  • DGX Station: models in the several-hundred-billion to trillion-parameter range when quantized, with the speed to serve several people at once.

Combining machines, and how they compare

You can link machines to run a model that does not fit on one. The pieces are connected over a network and the model is split across them (layers on one machine and layers on the next, or experts spread out). The link speed decides how well it works.

SetupHow it is combinedResult
Two DGX SparksDirect high-speed link (ConnectX-7 networking) as an officially supported pair256 GB combined, for models around 200B parameters at 4-bit
Several Mac StudiosThunderbolt or Ethernet with software such as MLX distributed or exoCombined memory for the biggest open models; speed limited by the link
Mac plus SparkMix: the Spark processes the long prompt, the Mac does the token generation (an approach community projects have demonstrated)Uses each machine's strength; experimental and fiddly
Station plus Spark or MacStation as the main server, others as extra capacity or for separate jobsUsually simpler to give each machine its own model than to split one
Compare on three axes

Capacity (which models fit), bandwidth (tokens per second), and compute (how quickly it reads a long prompt). Mac Studio wins on capacity per dollar, the Spark on software compatibility for its price, and the Station on all three at a much higher price. Combining machines adds capacity but rarely speed, so buy one machine large enough for your model before clustering.

A desktop RTX 5080 with 16 GB

A single gaming card is the most common local setup. The card has 16 GB of fast video memory (VRAM); everything beyond that must spill into system RAM, which is slower. Three models stand out for it:

ModelSize and typeContextHow it fits

Gemma 4 12B, QAT, instruction-tuned12B dense, quantization-aware trained256KThe QAT build is small enough to sit in 16 GB. Very long contexts use more memory, so expect to trim the context before you hit 256K.

Treat the context figures as maximums. Real speed and the usable context depend on your system RAM, the quantization, and the software. Test with your own prompts.

Comparing models: BenchLM

BenchLM is a leaderboard site that compares language models on quality, cost and context window. It tracks more than a thousand models and offers quick picks such as best open-weight model, best value, fastest, and largest useful context, plus comparison tools and a downloadable dataset.

  • Use it to: shortlist models, find the best open-weight option for your memory budget, and check cost against quality.
  • Remember: benchmark scores are not your task. Build your own small test set (see the Fine-Tuning pipeline) and run the shortlist through it.
