Generative AI

Generative AI creates new content (text, images, code, audio) rather than only labelling or predicting. This page covers how the main model families work, how to steer them with prompts, how to call them from code, and where the real limits are.

What makes it "generative"

A discriminative model answers "which category is this?". A generative model learns the shape of the data itself well enough to produce new samples that look like it. The ideas build directly on deep learning.

Model familyHow it generatesTypical output
Transformer-based (LLMs)Predicts the next token repeatedly, using attention over the whole contextText, code, summaries, translation
Diffusion modelsStarts from random noise and removes it step by step, guided by a text promptImages (Stable Diffusion, DALL-E)
Variational autoencoders (VAEs)Learn a compressed latent space and sample new points from itImages, interpolation between samples
GANsA generator and a discriminator compete, each improving the otherRealistic images and video

How large language models work

  • Tokens: text is split into small pieces (words or parts of words). Models read and write tokens, and usage is usually billed per token.
  • Pretraining: the model reads huge amounts of text and learns to predict the next token. This is where its broad knowledge and fluency come from.
  • Fine-tuning and instruction tuning: further training on examples of good behaviour, so the model follows instructions, keeps a consistent format and handles a specific domain.
  • Context window: the amount of text the model can consider at once. Anything outside it is invisible to the model.
  • Temperature: controls randomness. Low values give steadier, more repeatable answers; higher values give more varied ones. The full list of sampling settings (top_p, top_k, penalties and more) is on the Models page.
Fluent is not the same as correct

An LLM produces the most plausible continuation, not a verified fact. It can state wrong things confidently (called hallucination), so important outputs need checking.

Prompt engineering

The prompt is your main control over the output. Good prompting is clear writing, not magic words.

Zero-shot, few-shot and beyond

TechniqueWhat you doUse it when
Zero-shotGive an instruction with no examplesThe task is simple and common
Few-shotInclude a few worked examples inside the prompt so the model copies the pattern and styleYou need a specific format, tone or label set
Role / personaSay who the model should act as and for whomTone and depth matter
Step-by-step reasoningAsk it to work through the problem before answeringMaths, logic, multi-part problems
# Zero-shot
Summarize the following report in under 50 words.

# Few-shot: show the style you want
Report A summary: "Q1 sales rose 8% on strong retail demand; costs flat."
Report B summary: "Churn fell to 3% after the onboarding redesign."
Now summarize Report C in the same style.

Best practices

  1. Be specific. State the task, audience, length and what to leave out.
  2. Give context. Paste the relevant text or facts instead of assuming the model knows them.
  3. Specify the format. Bullet list, table, JSON with named keys, word limit.
  4. Set the tone and the role.
  5. Show examples when wording alone is ambiguous.
  6. Iterate. Read the output, tighten the prompt, run again.
Practical tip

Prompt engineering is also a cost lever. A precise prompt ("under 100 words, as a table") returns something you can use directly, so you do not spend more tokens on follow-up corrections. Vague prompts waste tokens, time and money.

Weak versus strong

WeakStrong
"Tell me about this customer issue.""Extract issue summary, likely cause, priority and recommended action from the text below. Return valid JSON with exactly those four keys, plus a two-column markdown table of the same fields. Use a neutral, professional tone."

The strong version states the fields, the output format, the strictness and the tone, and it produces something a program can parse.

Calling a model from Python

Hosted models are reached through an API. You authenticate with an API key, send a list of messages as JSON, and read the reply. The same pattern works across providers (OpenAI, Groq, Anthropic, and others); only the client and model name change.

import os, json
from groq import Groq                       # pip install groq

client = Groq(api_key=os.environ["GROQ_API_KEY"])   # never hard-code keys

prompt = """Extract these fields from the text: issue_summary, possible_cause,
priority, recommended_action. Return only valid JSON with those four keys.

Text: Customers report checkout fails after the 3pm deploy; error 500 on payment."""

resp = client.chat.completions.create(
    model="openai/gpt-oss-20b",
    messages=[{"role": "system", "content": "You are a precise support-triage assistant."},
              {"role": "user", "content": prompt}],
    temperature=0,
)
ticket = json.loads(resp.choices[0].message.content)   # JSON -> Python dict
print(ticket["priority"])
Why JSON matters

Asking for JSON turns a chatty answer into data your code can use: write it to a log, create a ticket, fill a database. Always validate it with json.loads inside a try block and retry or repair when the model returns malformed output. Keep API keys in environment variables, not in notebooks you share.

Giving a model your own knowledge: RAG and the LLM Wiki

There are two ways to hand a model your own documents without retraining it. The classic one is RAG. A newer one, published by Andrej Karpathy as the LLM Wiki pattern, has the same goal but changes where the work happens.

Classic RAG: retrieve at question time

Retrieval-augmented generation keeps the base model unchanged and hands it your data when a question arrives. Split your documents into chunks, turn each into an embedding (a vector of numbers capturing meaning), store them in a vector index, and at question time find the closest chunks and put them in the prompt. This gives domain-specific, up-to-date answers without retraining, and you can show the sources.

Its weakness, according to Karpathy: the model re-derives the answer from raw chunks on every question. Nothing is summarized or cross-linked ahead of time, so a question that needs several documents put together has to be assembled again each time, and nothing accumulates. He lists NotebookLM, ChatGPT file uploads and most RAG systems as examples.

The LLM Wiki: compile once, keep it current

In April 2026 Karpathy published an "idea file" (a gist, not code) describing a different pattern: instead of retrieving raw chunks, an LLM builds and maintains a wiki, a set of interlinked Markdown pages, from your sources. When a new source arrives, the LLM reads it, writes a summary, updates the related pages (one source may touch 10 to 15), flags contradictions and logs what it did. The knowledge is compiled once and kept up to date, so it compounds instead of being rebuilt for each question. You curate sources and ask questions; the LLM does the summarizing, cross-referencing and bookkeeping.

LayerWhat it isWho owns it
Raw sourcesArticles, papers, images, data files. Never edited; the source of truthYou
The wikiLLM-written Markdown: summaries, entity and concept pages, comparisons, an overviewThe LLM (you read it)
The schemaA config file such as CLAUDE.md or AGENTS.md that defines the wiki's structure, conventions and workflowsYou and the LLM, refined over time

How it actually works

  1. You add a source to the raw collection and ask the LLM to process it.
  2. The LLM reads it and discusses the key takeaways with you.
  3. It writes a summary page in the wiki, then updates index.md.
  4. It updates the related pages (people, concepts, comparisons), adding links and flagging where the new source contradicts older claims. One source may touch 10 to 15 pages.
  5. It appends an entry to log.md recording what it did.
  6. Later, when you ask a question, the LLM reads index.md first to find the relevant pages, opens those pages, and writes an answer with citations. No embeddings or vector search are part of this core loop. A good answer can be filed back into the wiki as a new page.

The key difference from RAG: the synthesis (links, summaries, contradictions) is done when a source arrives and saved in the wiki, so at question time the LLM reads finished, connected pages instead of raw fragments. You almost never write the wiki yourself. You choose the sources, steer the analysis, ask questions and review what the LLM changes (for example by browsing the files in Obsidian).

Three operations

  • Ingest: read a new source, discuss the takeaways, write its summary page, update the index and related pages, and add an entry to the log. Ingesting one source at a time keeps you in the loop.
  • Query: the LLM reads the index, opens the relevant pages and answers with citations. The answer can be a page, table, slide deck or chart, and good answers can be filed back into the wiki so explorations accumulate.
  • Lint: periodic health checks for contradictions, stale claims, orphan pages, missing concept pages, missing cross-references and gaps that a web search could fill.

Two special files

  • index.md: a catalog of every page with a link and a one-line summary, organized by category. The LLM reads it first when answering. The gist says this works at moderate scale (around 100 sources and a few hundred pages) without embedding infrastructure.
  • log.md: an append-only record of ingests, queries and lint passes, with consistent prefixes so ordinary command-line tools can parse it.

Where search fits

At first the LLM Wiki replaces vector search: the LLM navigates with index.md, which the gist says is enough at about 100 sources and a few hundred pages. As the wiki grows past that, the gist suggests adding a proper search tool (for example qmd, which combines keyword and vector search with re-ranking, or a simple script the LLM writes for you). That search runs over the wiki pages the LLM wrote, not over raw document chunks. The gist does not say how the pattern behaves for very large archives, so do not assume it replaces RAG there. The Finetuning an LLM pipeline uses a similar layout: sources in raw/, cleaned notes in wiki/, run logs in traces/. More on the gist is on the AI Pioneers page.

Agentic AI

A standard model answers a prompt. An agent goes further: it plans, picks tools (search, code, email, databases), carries out steps and checks the result, with limited human intervention. An onboarding agent, for example, could read a request, create accounts, send emails and log what it did. Self-driving cars are a physical-world cousin. The more freedom an agent has, the more it needs permission limits, logging and human approval for risky actions.

Responsible AI: bias, privacy and security

  • Bias. Models reflect their training data. If the data under-represents or stereotypes a group, outputs will too. Mitigate with diverse, representative data, testing across groups, human review, and reporting problems to the model provider. RAG over vetted data can also help steer outputs.
  • Privacy. Do not paste confidential or personal data into tools you do not control. Privacy-preserving approaches include federated learning, where training happens on local devices and only model updates are shared, not raw data. Consent over training data is an open legal and ethical question.
  • Security. Models and agents can be tricked by hostile text (prompt injection), and data can leak through careless use. Treat model output and any outside text as untrusted input.
  • Governance. Know who owns the data, how it is stored, what is logged and who is accountable for decisions.

Will AI replace jobs?

The realistic view: generative AI changes how work is done more than it removes whole roles. It speeds up drafting, coding and analysis, so a person can act as a reviewer who validates the output rather than writing everything from scratch. Reasons it does not simply replace people:

  • Cost. Running large models at scale is expensive, so automating everything is often uneconomical.
  • Errors. Even strong models make mistakes, including in code, so humans must check results.
  • Accountability. Someone has to own the decision, handle edge cases and understand the business context.

The practical takeaway is to learn to work with these tools: write good prompts, verify outputs and know their limits.

A quick checklist before you ship an AI feature

  1. Is the prompt specific, with a defined output format?
  2. Are outputs validated before anything acts on them?
  3. Is a person in the loop for high-stakes decisions?
  4. Are keys, personal data and secrets kept out of prompts and code?
  5. Have you tested for bias and for failure cases?
  6. Do you know the cost per request at your expected volume?

More on governance, tools and prompting tips

Details

Points that go beyond the sections above.

Regulation and governance

  • EU AI Act: classifies AI systems by risk. GDPR: limits how personal data may be stored and used. US executive orders give guidance on responsible AI use.
  • Governance components: risk assessment, compliance monitoring, a human in the loop, and accountability shared among developers, organizations and policymakers.
  • Explainable AI principles: interpretability, traceability, accountability and algorithmic transparency.

Security, bias and privacy

  • Threats named in class: data poisoning, model inversion, deepfakes and misinformation, and prompt injection.
  • Bias mitigation: fairness audits and diverse training data. If the bias comes from the base model you cannot remove it, so report it to the provider; supplying your own data through RAG can counter it.
  • Privacy practices: data anonymization and user-consent mechanisms. Federated learning keeps raw data on the device (phone face unlock is an example).
  • Cost and sustainability: data centres strain water and local ecology, memory and compute prices have risen sharply, and token costs are rising.

Physical AI and model families

  • Physical AI acts in the real world through robots, drones, exoskeletons and self-driving cars. Self-driving cars combine physical and agentic AI.
  • Model names mentioned: BERT (bidirectional, for understanding text), GPT (generates text), T5 (text-to-text), and image tools such as Art Breeder, DeepArt and Runway ML.

Prompting and API tips

  • Build reusable prompt templates and train your team to prompt well. Iterate after a first detailed prompt.
  • For resumes and profiles, add “use only the information given; do not invent anything” because these prompts hallucinate. Cross-check translations with another tool.
  • Ask the model to check itself: validate output more than once, make the simplest change, remove dead code, and validate code flow and data flow.
  • API access: an API key is the minimum. Sensitive flows also need a user ID and a secret token. Model IDs get deprecated (older hosted Llama models have been retired), so be ready to change them.
