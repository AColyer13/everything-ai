Models

Where AI models actually run. The hardware NVIDIA sells to enterprises for cloud models, the desktop machines that run big models locally (Mac Studio, DGX Spark, DGX Station), what a single 16 GB RTX 5080 can do, the main kinds of models, and how to compare them.

Speeds and memory needs are estimates; verify before you buy hardware. The software that runs these models is on the Tools page.

The one rule: memory decides everything

A model's weights must sit in fast memory while it runs. Rough sizing: file size in GB is about parameters (in billions) × bytes per weight. At 16-bit that is 2 bytes, at 8-bit 1 byte, at 4-bit about 0.5 byte. Add room for the KV cache (the model's working memory of the conversation), which grows with context length.

Two numbers matter on any machine: capacity (can the model fit at all) and bandwidth (how fast the chip can read it, which sets tokens per second). This is why a 512 GB machine can load a huge model yet generate slowly, while a 16 GB GPU is fast but limited to small ones.

NVIDIA in the enterprise: how cloud models run

Cloud models such as Claude, GPT and Gemini are too large for any one chip, so providers run them across racks of data-center accelerators. NVIDIA sells most of that hardware.

Clouds sell this as an API (you pay per token) or as rented GPUs (you pay per hour, for example for the 8×H100 runs on the LLM page). Enterprises also buy the hardware for their own data centers when data cannot leave the building.

Parameter size: what the number means

A parameter is one learned number in the network. More parameters usually means more knowledge and better reasoning, at the cost of memory and speed.

Dense versus mixture of experts (MoE)

A dense model uses all its parameters for every token. A mixture-of-experts model holds many specialist sub-networks and activates only a few per token. A "125B" MoE model that activates about 6B parameters per token needs memory for all 125B but reads only about 6B per token, so it generates much faster than a dense 125B model. That trick is what makes huge models usable on desktop machines.

Quantization

Quantization stores each weight with fewer bits. A full-precision weight takes 2 to 4 bytes; a 4-bit weight takes half a byte. The file shrinks, it fits in less memory, and generation gets faster because fewer bytes are read per token (see the bandwidth rule on the Hardware page). The cost is some loss of quality, small at 8 and 4 bits and growing below that.

Size rule of thumb: file size in GB is about parameters in billions × bits ÷ 8, plus 10% to 20% for overhead. A 20B model is about 40 GB at 16-bit, 20 GB at 8-bit and 10 GB at 4-bit.

The two ways to get a quantized model

  • Post-training quantization (PTQ): take a finished model and compress its weights afterward. Quick and cheap, and almost every file you download from the community is made this way. Quality drops more as the bit count falls.
  • Quantization-aware training (QAT): the model is trained or fine-tuned while simulating the low precision, so it learns to work around the rounding. A QAT 4-bit model (such as Google's Gemma 4 QAT checkpoints) keeps noticeably more quality than the same model compressed afterward.

How to choose

  • Use the highest precision that fits in your fast memory with room left for the context (KV cache). If 8-bit fits, take it; if not, 4-bit.
  • A larger model at 4-bit usually beats a smaller model at 8-bit, so it is often better to quantize a bigger model than to run a small one at full quality.
  • Go below 4-bit only when you have to, as with a 125B model on a 16 GB card. Expect some quality loss, and prefer I-quants or dynamic quants at 2 to 3 bits.
  • Quantization shrinks the weights, not the context. The KV cache that grows with context length has its own memory cost, and some runners can quantize it too.
  • Prefer a QAT release when one exists, because it loses the least at 4-bit.

Context length

The context window is how much text the model can consider at once (128K tokens is roughly a 300-page book). Longer context costs memory for the KV cache and slows prompt processing, so a model that "supports" 256K may not fit 256K on your hardware.

A desktop RTX 5080 with 16 GB

For how this card compares with the B200, DGX Station and Spark, and Apple's M5 and M6 chips, see the Hardware page.

A single gaming card is the most common local setup. The card has 16 GB of fast video memory (VRAM); everything beyond that must spill into system RAM, which is slower. Three models stand out for it:

Which software runs which model

Gemma 4 12B QAT and gpt-oss-20b are small enough to fit in the 16 GB card, so any of the mainstream engines can run them: Ollama, LM Studio or vLLM. Qwen3.8-Flash-Next (125B) does not fit, and it needs a new architecture that mainline llama.cpp did not support at the time of writing, so it runs through Strata (or a custom llama.cpp build).

The difference in one line: Ollama, LM Studio and vLLM are general engines for models that fit in memory. Strata is a specialist that makes one 125B mixture-of-experts model usable by treating RAM and SSD as extra memory and reading only the roughly 6B active parameters for each token, with a small helper model drafting words that the big model verifies. Support for new models in the general engines tends to arrive over time, so check before you assume a model can run.

Treat the context figures as maximums. Real speed and the usable context depend on your system RAM, the quantization, and the software. Test with your own prompts.

Comparing models: BenchLM

BenchLM is a leaderboard site that compares language models on quality, cost and context window. Its own pages report between about 400 tracked models and about 1,000 model profiles (the count changes as it updates), with scores built from published benchmark results rather than private tests. It offers quick picks such as best open-weight model, best value, fastest, and largest useful context, plus comparison tools and a downloadable dataset.

  • Use it to: shortlist models, find the best open-weight option for your memory budget, and check cost against quality.
  • Remember: benchmark scores are not your task. Build your own small test set (see the Finetuning an LLM pipeline) and run the shortlist through it.
