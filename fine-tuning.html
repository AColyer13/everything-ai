Fine-Tuning

The recommended pipeline for improving a local language model on one 16 GB GPU. Written Nov 4, 2026 by Adam.

Not from the class

This page is a practical guide added on top of the course content. It builds on Deep Learning (transfer learning) and Generative AI (fine-tuning versus RAG). Model names, sizes and release dates are as of the date above and change quickly, so check the model cards before you start.

Summary

The recommended way to improve a local model on one 16 GB GPU is: build an eval set, ground the model with retrieval, optimize the prompt, then distill the best verified outputs into a QLoRA adapter and ship it as a quantized GGUF. Everything past that is optional and only triggered by a measured failure.

This version corrects an earlier draft playbook in four places:

  • Model IDs and memory math. The real IDs are Qwen/Qwen3.5-9B and google/gemma-4-12B-it. The 16-bit sizes are about 18 GB and 27 GB, not 24 GB.
  • Training batch size. Batch 2 at 8,192 tokens is too tight for 16 GB. Start at batch 1 with gradient accumulation 8.
  • Weight surgery (abliteration). Demoted from a pipeline step to an experiment. It is proven for refusal removal, unproven for sycophancy or loops, and it weakens safety behavior by design.
  • autoresearch ratchet. Demoted. It was built for 5-minute from-scratch pretraining on an H100, not for fine-tuning a 9B model. Tune against the task benchmark instead of validation loss.

Hardware and model choices

Target machine: RTX 5070 Ti (16 GB VRAM) with 64 GB system RAM. Qwen3.5-9B is the safer default for training on this card. Gemma 4 12B fits for inference but is tight for QLoRA at long context.

What fits on 16 GB

  • Training (QLoRA, 4-bit base): 9B fits comfortably at 4k–8k context with batch 1. 12B fits at batch 1 with shorter context; expect to drop to 4k.
  • Merging and weight edits (16-bit): neither model fits in VRAM. Use CPU offload into the 64 GB of system RAM.
  • Inference: 9B at Q8_0 (~9.5 GB) or 12B at Q4_K_M (~7 GB) both leave room for the KV cache.

The pipeline

Six core steps, in order. The benchmark from step 1 is the single yardstick for every later decision. Steps 1–4 build the data; steps 5–6 build the model. A model that doesn't beat the prompted base goes to the optional fixes, then back through training.

  1. Build the evaluation set first. 50–100 real domain questions with known-good answers and a scoring script (schema valid, citations correct, answer correct). Hold out a separate test split that is never used for tuning.
  2. Ground the model with retrieval. Keep source documents in raw/, cleaned and cross-referenced notes in wiki/, and log every run to traces/ as JSONL (prompt, retrieved context, response, score, latency). Fine-tuning teaches format and reasoning style, not facts, so facts stay in retrieval. (See RAG on the Generative AI page.)
  3. Optimize the prompt before touching weights. Define input/output signatures and let DSPy / GEPA search instructions and few-shot examples against the scoring script. Use a larger teacher model here if the local model can't reach the target score on its own.
  4. Harvest the dataset. Keep traces that pass the scoring script, including the retrieved context inside each prompt. Aim for 300–1,000 examples in ChatML dataset.jsonl. Deliberately keep hard cases, not only the easy ones that score highest.
  5. Train a QLoRA adapter with Unsloth. Use the configuration in the next section, 1–3 epochs, and stop on validation loss. Score the adapter on the benchmark, not just the loss curve.
  6. Merge, quantize and verify. Merge the adapter into the 16-bit base, convert to GGUF, build an importance matrix with llama-imatrix from your own domain prompts, quantize to Q8_0 (9B) or Q4_K_M (12B), load with ollama create, and re-run the benchmark. Ship only if the quantized model still beats the prompted base model.

If step 6 shows a specific, repeatable failure, go to the optional steps below. Otherwise you're done.

Risks and pitfalls

  • Self-distillation has a ceiling. Training on the same model's best prompted outputs mostly buys shorter prompts and faster inference, not new capability. For real gains, generate the dataset with a stronger teacher model.
  • Easy-case bias. Filtering for only the top-scoring outputs drops hard examples, so the model gets worse on exactly the cases that matter.
  • Benchmark leakage. If test questions or their wiki context end up in training data, scores will look better than real performance.
  • Quantization loss. Gains can shrink at Q4. Always re-score after quantizing.
  • Chat template mismatch. Training and Ollama inference must use the same template, or output quality drops sharply.
  • Out of memory. Long context is the usual cause on 16 GB. Cut sequence length before cutting rank.

Day-1 checklist

  • ☐ Write a 50-question benchmark with a scoring script and a held-out test split
  • ☐ Load clean domain knowledge into wiki/ and turn on trace logging
  • ☐ Optimize the prompt (DSPy / GEPA) and record the prompted-base score
  • ☐ Harvest 300–500 verified, context-grounded examples into dataset.jsonl
  • ☐ Train QLoRA on Qwen/Qwen3.5-9B with the baseline config (r = 16, lr 2e-4, batch 1 × 8, 4k context)
  • ☐ Merge, quantize with imatrix to Q8_0, load in Ollama
  • ☐ Re-run the benchmark; ship only if it beats the prompted base
