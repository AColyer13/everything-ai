Generative AI

Generative AI creates new content (text, images, code, audio) rather than only labelling or predicting. This page covers how the main model families work, how to steer them with prompts, how to call them from code, and where the real limits are.

What makes it "generative"

A discriminative model answers "which category is this?". A generative model learns the shape of the data itself well enough to produce new samples that look like it. The ideas build directly on deep learning.

Model familyHow it generatesTypical output
Transformer-based (LLMs)Predicts the next token repeatedly, using attention over the whole contextText, code, summaries, translation
Diffusion modelsStarts from random noise and removes it step by step, guided by a text promptImages (Stable Diffusion, DALL-E)
Variational autoencoders (VAEs)Learn a compressed latent space and sample new points from itImages, interpolation between samples
GANsA generator and a discriminator compete, each improving the otherRealistic images and video

How large language models work

  • Tokens: text is split into small pieces (words or parts of words). Models read and write tokens, and usage is usually billed per token.
  • Pretraining: the model reads huge amounts of text and learns to predict the next token. This is where its broad knowledge and fluency come from.
  • Fine-tuning and instruction tuning: further training on examples of good behaviour, so the model follows instructions, keeps a consistent format and handles a specific domain.
  • Context window: the amount of text the model can consider at once. Anything outside it is invisible to the model.
  • Temperature: controls randomness. Low values give steadier, more repeatable answers; higher values give more varied ones.
Fluent is not the same as correct

An LLM produces the most plausible continuation, not a verified fact. It can state wrong things confidently (called hallucination), so important outputs need checking.

Prompt engineering

The prompt is your main control over the output. Good prompting is clear writing, not magic words.

Zero-shot, few-shot and beyond

TechniqueWhat you doUse it when
Zero-shotGive an instruction with no examplesThe task is simple and common
Few-shotInclude a few worked examples inside the prompt so the model copies the pattern and styleYou need a specific format, tone or label set
Role / personaSay who the model should act as and for whomTone and depth matter
Step-by-step reasoningAsk it to work through the problem before answeringMaths, logic, multi-part problems
# Zero-shot
Summarize the following report in under 50 words.

# Few-shot: show the style you want
Report A summary: "Q1 sales rose 8% on strong retail demand; costs flat."
Report B summary: "Churn fell to 3% after the onboarding redesign."
Now summarize Report C in the same style.

Best practices

  1. Be specific. State the task, audience, length and what to leave out.
  2. Give context. Paste the relevant text or facts instead of assuming the model knows them.
  3. Specify the format. Bullet list, table, JSON with named keys, word limit.
  4. Set the tone and the role.
  5. Show examples when wording alone is ambiguous.
  6. Iterate. Read the output, tighten the prompt, run again.
From the live classes

Prompt engineering is also a cost lever. A precise prompt ("under 100 words, as a table") returns something you can use directly, so you do not spend more tokens on follow-up corrections. Vague prompts waste tokens, time and money.

Weak versus strong

WeakStrong
"Tell me about this customer issue.""Extract issue summary, likely cause, priority and recommended action from the text below. Return valid JSON with exactly those four keys, plus a two-column markdown table of the same fields. Use a neutral, professional tone."

The strong version states the fields, the output format, the strictness and the tone, and it produces something a program can parse.

Calling a model from Python

Hosted models are reached through an API. You authenticate with an API key, send a list of messages as JSON, and read the reply. The same pattern works across providers (OpenAI, Groq, Anthropic, and others); only the client and model name change.

import os, json
from groq import Groq                       # pip install groq

client = Groq(api_key=os.environ["GROQ_API_KEY"])   # never hard-code keys

prompt = """Extract these fields from the text: issue_summary, possible_cause,
priority, recommended_action. Return only valid JSON with those four keys.

Text: Customers report checkout fails after the 3pm deploy; error 500 on payment."""

resp = client.chat.completions.create(
    model="openai/gpt-oss-20b",
    messages=[{"role": "system", "content": "You are a precise support-triage assistant."},
              {"role": "user", "content": prompt}],
    temperature=0,
)
ticket = json.loads(resp.choices[0].message.content)   # JSON -> Python dict
print(ticket["priority"])
Why JSON matters

Asking for JSON turns a chatty answer into data your code can use: write it to a log, create a ticket, fill a database. Always validate it with json.loads inside a try block and retry or repair when the model returns malformed output. Keep API keys in environment variables, not in notebooks you share.

Giving a model your own knowledge: RAG

Retrieval-augmented generation keeps the base model unchanged and hands it your data at question time. The flow is: split your documents into chunks, turn each into an embedding (a vector of numbers capturing meaning), store them in a vector index, and when a question arrives, find the closest chunks and put them in the prompt. This gives domain-specific, up-to-date answers without retraining, and you can show the sources.

Agentic AI

A standard model answers a prompt. An agent goes further: it plans, picks tools (search, code, email, databases), carries out steps and checks the result, with limited human intervention. An onboarding agent, for example, could read a request, create accounts, send emails and log what it did. Self-driving cars are a physical-world cousin. The more freedom an agent has, the more it needs permission limits, logging and human approval for risky actions.

Responsible AI: bias, privacy and security

  • Bias. Models reflect their training data. If the data under-represents or stereotypes a group, outputs will too. Mitigate with diverse, representative data, testing across groups, human review, and reporting problems to the model provider. RAG over vetted data can also help steer outputs.
  • Privacy. Do not paste confidential or personal data into tools you do not control. Privacy-preserving approaches include federated learning, where training happens on local devices and only model updates are shared, not raw data. Consent over training data is an open legal and ethical question.
  • Security. Models and agents can be tricked by hostile text (prompt injection), and data can leak through careless use. Treat model output and any outside text as untrusted input.
  • Governance. Know who owns the data, how it is stored, what is logged and who is accountable for decisions.

Will AI replace jobs?

The realistic view from the class discussion: generative AI changes how work is done more than it removes whole roles. It speeds up drafting, coding and analysis, so a person can act as a reviewer who validates the output rather than writing everything from scratch. Reasons it does not simply replace people:

  • Cost. Running large models at scale is expensive, so automating everything is often uneconomical.
  • Errors. Even strong models make mistakes, including in code, so humans must check results.
  • Accountability. Someone has to own the decision, handle edge cases and understand the business context.

The practical takeaway is to learn to work with these tools: write good prompts, verify outputs and know their limits.

A quick checklist before you ship an AI feature

  1. Is the prompt specific, with a defined output format?
  2. Are outputs validated before anything acts on them?
  3. Is a person in the loop for high-stakes decisions?
  4. Are keys, personal data and secrets kept out of prompts and code?
  5. Have you tested for bias and for failure cases?
  6. Do you know the cost per request at your expected volume?
