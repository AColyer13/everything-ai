Loops

44 repeatable loops for agents, engineering, management, product, data science, research and writing. Each one lists where it comes from, what each stage or worker does, and when it stops. To design a new loop, start here and borrow the stage you are missing.

Not from the class

This page is a reference collection added on top of the course content. Loops marked ★ come from Andrej Karpathy (see AI Pioneers). Click a loop to open it.

AI agents

ReActReason → Act → Observe

Origin: AI research (Yao et al., 2022). The basic loop behind most tool-using agents.

  1. Reason: The agent thinks out loud about what it knows and what to do next.
  2. Act: It calls one tool, such as search, a file read or a shell command.
  3. Observe: It reads the tool's result and adds it to its context, then reasons again.

Exit: The agent has enough to answer, or it hits a step limit.

AnthropicExplore → Plan → Code → Commit

Origin: Anthropic's recommended Claude Code workflow. For coding agents in existing repos.

  1. Explore: Read the relevant files, tests and docs. Write no code yet.
  2. Plan: Write a step-by-step plan and have a human approve it.
  3. Code: Implement the plan and check each step against tests.
  4. Commit: Write the commit message and open a PR.

Exit: The PR is open and tests pass.

Dexter HorthyResearch → Plan → Implement

Origin: AI-agent engineering. For long tasks that would fill up the context window.

  1. Researcher: Maps how the code works today and writes research.md.
  2. Planner: Starts from fresh context, reads only research.md, and writes plan.md with exact files and steps.
  3. Implementer: Starts from fresh context, works through plan.md and ticks off steps as it goes.

Exit: Every step in plan.md is done and verified.

Spec-drivenSpecify → Plan → Tasks → Implement

Origin: GitHub Spec Kit. For features with clear requirements.

  1. Specify: Describe what to build and why, as user stories and acceptance criteria. Leave out the tech choices.
  2. Plan: Choose the stack, architecture and constraints.
  3. Tasks: Break the plan into small tasks that can each be reviewed alone.
  4. Implement: The agent completes tasks one by one, checking each against the spec.

Exit: Every acceptance criterion in the spec is met.

Evaluator-OptimizerGenerate → Critique → Revise

Origin: Anthropic's "Building effective agents" patterns. For any output with a quality bar.

  1. Generator: Writes the first draft.
  2. Evaluator: Scores the draft against a rubric and lists specific problems.
  3. Generator (again): Revises only what the evaluator flagged.

Exit: The evaluator's score clears the bar, or after N rounds.

Related: GAN training (Ian Goodfellow, 2014) is the adversarial version. The generator makes, the discriminator judges, and both improve against each other.

ReflexionAttempt → Fail → Reflect → Retry

Origin: AI research (Shinn et al., 2023). For tasks the agent fails at first.

  1. Actor: Attempts the task.
  2. Evaluator: Checks the result with tests or a grader.
  3. Reflector: On failure, writes a short note in plain words saying what went wrong and what to try instead.
  4. Memory: Stores the note so the actor reads it on the next attempt.

Exit: A pass, or the retry limit.

Best-of-N + VerifierN generators → Verifier → Selector

Origin: AI research and agent engineering. For problems with several workable answers.

  1. N generators: Each solves the same problem independently, in parallel, with varied prompts or temperature.
  2. Verifier: Runs tests or a judge model on every candidate.
  3. Selector: Keeps the best candidate, or merges the strongest parts.

Exit: One candidate passes verification. If none do, raise N or rethink the prompt.

AnthropicOrchestrator → Workers → Synthesizer

Origin: Anthropic's "Building effective agents" patterns. For big tasks that split into parallel parts.

  1. Orchestrator: Splits the task into independent subtasks and writes a clear brief for each one.
  2. Workers: Each handles one subtask in its own context and returns a summary.
  3. Synthesizer: Merges the results, resolves conflicts and fills gaps.

Exit: Every subtask is returned and the merged result passes review.

DebateProponent → Opponent → Rebuttal rounds → Judge

Origin: AI safety research. For decisions and trade-offs.

  1. Proponent: Makes the strongest case for option A.
  2. Opponent: Makes the strongest case for option B, or against A.
  3. Rebuttal rounds: Each side answers the other's best point.
  4. Judge: Weighs the arguments and decides, with reasons.

Exit: The judge rules, usually after 2–3 rounds.

Ralph loopPrompt file → Agent run → Repeat

Origin: Geoffrey Huntley. For long unattended builds.

  1. Prompt file: One fixed prompt describes the goal and points the agent to a task list.
  2. Agent run: Each run picks the next task, does it and updates the files.
  3. Repeat: A while true shell loop starts a fresh agent with the same prompt. Progress lives in git and files, not in context.

Exit: The task list is empty, or a human stops the loop.

Team-solvePlan → 2 Ideators → Solver → Manager → Repair → Test

Origin: The team-solve repo on GitHub. For hard or open-ended problems that benefit from more than one approach.

  1. Planner: Defines the problem, the meaning of "done" and the tests or rubric before anyone builds.
  2. Ideator 1 and Ideator 2: Each proposes a solution independently, with different prompts or angles, so their ideas don't converge too early.
  3. Solver: Takes the best parts of both ideas and builds one working solution.
  4. Manager: Reviews the solution against the plan and the rubric, then lists specific problems to fix.
  5. Repair: Fixes only what the manager flagged.
  6. Test: Runs the tests. On failure, the loop goes back to Repair. If the approach itself is wrong, it goes back to the Ideators.

Exit: All tests pass and the manager approves. Cap the number of repair rounds and escalate to a human if the cap is hit.

★ Karpathy AutoResearchProgram → Edit → Train → Measure → Keep or Revert → Repeat

Origin: Andrej Karpathy's autoresearch repo, March 2026. For overnight, unattended ML experiments. In his demo, the agent ran about 700 experiments over two days and found about 20 improvements.

  1. Program (human): Write program.md with the goal, the constraints and when to stop. This is the only file the human writes.
  2. Edit (agent): Change one thing in train.py, such as a hyperparameter or an architecture choice. This is the only file the agent may touch.
  3. Train: Run for a fixed time budget, so every experiment is directly comparable.
  4. Measure: Read one objective metric (validation bits per byte).
  5. Keep or revert: If the metric improved, commit to git. If not, discard the change.
  6. Repeat: Start the next experiment from the best version so far.

Exit: The stopping rule in program.md, a time limit, or progress stalls. Karpathy's rules: write a verifier, cap the retries, and give the agent more autonomy as the verifier proves itself.

Meta-HarnessPropose → Run → Store → Search → Repeat

Origin: Researchers at Stanford, MIT and KRAFTON (2026). It applies AutoResearch to the harness instead of the training code. The model stays frozen while the code around it (prompts, tools, memory, loop logic) improves. For tuning an agent to a specific task or benchmark.

  1. Proposer (coding agent): Writes a new version of the harness.
  2. Run: The harness is tested on a benchmark.
  3. Store: The harness's code, score and full execution traces go into a shared folder.
  4. Search: The proposer reads every past attempt, especially the failure traces, before writing the next one.
  5. Repeat: The best harness so far is the new baseline.

Exit: The benchmark score stops improving, or the budget runs out. Review each new harness like any other code before shipping it.

Tree of ThoughtsGenerate → Evaluate → Expand or Backtrack

Origin: AI research (Yao et al., 2023). For puzzles, planning and problems where the first idea is often a dead end.

  1. Generate: Propose several possible next steps ("thoughts") from the current state.
  2. Evaluate: Score each one as promising, maybe or a dead end.
  3. Expand: Continue from the best ones, searching breadth-first or depth-first.
  4. Backtrack: When a path dies, return to the last good branch.

Exit: A path reaches a verified solution, or the search budget runs out.

Eval-Driven DevelopmentBuild evals → Baseline → Change → Run evals → Read failures → Grow the eval set

Origin: Common practice for building LLM apps. It's TDD for prompts, models and agents. For any feature powered by a model.

  1. Build evals: Write 20–100 real test cases, each with a pass/fail check or a graded rubric.
  2. Baseline: Score the current system.
  3. Change: Adjust one thing, such as the prompt, model, tools or retrieval.
  4. Run evals: Score again and compare with the baseline. Keep the change only if it doesn't cause regressions.
  5. Read failures: Hand-read the failing cases and group them by type.
  6. Grow the eval set: Add every new failure from production as a new test case.

Exit: The eval pass rate hits the target with no regressions.

Software engineering

TDDRed → Green → Refactor

Origin: Kent Beck, Extreme Programming. For feature code and bug fixes.

  1. Red: Write one small test for the next behavior and watch it fail.
  2. Green: Write the least code that makes the test pass.
  3. Refactor: Clean up names and duplication while the tests stay green.

Exit: Every required behavior has a passing test.

Incident responseDetect → Triage → Mitigate → Resolve → Postmortem

Origin: Ops and SRE practice (Google SRE). For production outages.

  1. Detect: Monitoring or a user reports the problem, and someone is paged.
  2. Triage: The incident commander rates severity, assigns roles and opens a channel.
  3. Mitigate: Stop the bleeding with a rollback, feature flag or failover. Fix the cause later.
  4. Resolve: Find and fix the root cause.
  5. Postmortem: Write up the timeline, root cause and action items, without blame.

Exit: Service is restored and the postmortem's action items have owners.

DevOps infinity loopCode → Build → Test → Release → Deploy → Monitor

Origin: The DevOps movement. For shipping continuously.

  1. Code: Developers merge small changes often.
  2. Build: CI compiles the code and packages artifacts.
  3. Test: The automated suite gates every change.
  4. Release: The change is versioned and approved.
  5. Deploy: It rolls out, often behind flags or canaries.
  6. Monitor: Metrics and errors flow back and shape the next code change.

Exit: None. The loop runs continuously, and each change exits once it's healthy in production.

Scrum SprintPlan → Build → Daily sync → Review → Retro

Origin: Ken Schwaber and Jeff Sutherland, The Scrum Guide. For teams shipping in fixed 1–4 week cycles.

  1. Sprint planning: The team picks a sprint goal and pulls work from the backlog.
  2. Build: The team works on the sprint backlog.
  3. Daily scrum: A 15-minute sync on progress toward the goal and what's blocking it.
  4. Sprint review: Demo the working increment to stakeholders and update the backlog.
  5. Retrospective: The team picks one or two process changes for the next sprint.

Exit: The sprint ends on a fixed date, and then the next one starts. The product backlog drives when the whole effort ends.

Management and quality

PDCAPlan → Do → Check → Act

Origin: W. Edwards Deming. For any process improvement.

  1. Plan: State the goal and how you'll measure it.
  2. Do: Run the change on a small scale.
  3. Check: Compare the results with the goal.
  4. Act: If it worked, make it the standard. If not, adjust and plan again.

Exit: The goal is met and the change is the new standard.

OODAObserve → Orient → Decide → Act

Origin: John Boyd, US Air Force. For fast decisions under uncertainty.

  1. Observe: Gather raw information about what is happening now.
  2. Orient: Interpret it through context, experience and possible biases. This is the most important step.
  3. Decide: Choose a course of action.
  4. Act: Carry it out, then observe again right away.

Exit: The situation is resolved. The aim is to cycle faster than the situation changes.

DMAICDefine → Measure → Analyze → Improve → Control

Origin: Six Sigma. For cleanup work you can measure.

  1. Define: Name the problem, scope and target.
  2. Measure: Record baseline numbers.
  3. Analyze: Find the root causes from the data.
  4. Improve: Fix the top causes and measure again.
  5. Control: Add checks, alerts or CI rules so the gains stick.

Exit: The target is reached and controls are in place.

MAPE-KMonitor → Analyze → Plan → Execute over shared Knowledge

Origin: IBM autonomic computing. For systems that adjust themselves.

  1. Monitor: Sensors collect metrics and events.
  2. Analyze: Detect when the system drifts from its goals.
  3. Plan: Choose an adaptation, such as scaling up or rerouting.
  4. Execute: Apply it through effectors.
  5. Knowledge: A shared store of models, policies and history that every stage reads and updates.

Exit: None. It runs continuously, and each adaptation exits once the metrics are back in range.

Musk's AlgorithmQuestion → Delete → Simplify → Accelerate → Automate

Origin: Elon Musk's rules for SpaceX and Tesla production, made widely known by Walter Isaacson's 2023 biography of Musk. For code, frameworks and tools that have grown bloated. The order is strict: never do a step before the ones above it.

  1. Question (make requirements less dumb): Challenge every feature, requirement and assumption, and give each one a named owner. Cut each one down to the simplest version that still delivers the core value.
  2. Delete: Remove code, features, dependencies, logic, listeners and process steps. Aim for at least a 10% net reduction in lines of code, files or dependencies.
  3. Add-back check: Restore only what breaks the core value. Musk's rule: if you don't end up adding back at least 10% of what you deleted, you didn't delete enough.
  4. Simplify or optimize: Polish only what survived. Improve readability, performance and modularity. Never optimize something that shouldn't exist.
  5. Accelerate: Shorten the dev, test and deploy cycle on the leaner result.
  6. Automate: Lock in the gains with scripts, CI gates and hooks. This comes last because automating earlier locks in waste.

Exit: A pass removes nothing meaningful, every requirement has an owner, and the cycle time and automation are in place.

How it loops: Each pass ends with a smaller, faster, automated system. The next pass starts again at Question, against the new baseline. If the add-back check restores more than expected, go back to Question, because a requirement was wrong.

Product and design

Build → Measure → Learn

Origin: Eric Ries, The Lean Startup. For product bets and MVPs.

  1. Build: Ship the smallest version that tests one assumption.
  2. Measure: Track a metric tied to that assumption, such as signups, retention or conversion.
  3. Learn: Decide whether to persevere, pivot or kill the idea.

Exit: The assumption is proven or disproven with data.

Design ThinkingEmpathize → Define → Ideate → Prototype → Test

Origin: IDEO and the Stanford d.school. For user-facing products.

  1. Empathize: Interview and observe real users.
  2. Define: Write the core user problem as one problem statement.
  3. Ideate: Generate many possible solutions without judging them.
  4. Prototype: Build quick, cheap versions of the best ideas.
  5. Test: Put the prototypes in front of users and learn what works.

Exit: A prototype solves the defined problem in user tests.

Double DiamondDiscover → Define → Develop → Deliver

Origin: UK Design Council. For widening options, then narrowing them.

  1. Discover (diverge): Research the problem space broadly.
  2. Define (converge): Narrow it down to the one problem worth solving.
  3. Develop (diverge): Explore many solutions.
  4. Deliver (converge): Test them, pick one and ship it.

Exit: One solution is shipped.

Data and ML

CRISP-DMBusiness understanding → Data understanding → Data preparation → Modeling → Evaluation → Deployment

Origin: A cross-industry data mining standard from 1999. For data and ML projects.

  1. Business understanding: Define the question and what success looks like.
  2. Data understanding: Explore the data's sources, quality and gaps.
  3. Data preparation: Clean, join and engineer features.
  4. Modeling: Train candidate models.
  5. Evaluation: Check the results against the business goal, not only accuracy.
  6. Deployment: Ship the model and monitor it. Loop back when data or goals change.

Exit: The model is deployed and meets the business goal.

Train → Eval → Error analysis → Adjust

Origin: Everyday ML practice. For iterating on a model.

  1. Train: Fit the model on the training set.
  2. Eval: Score it on a held-out set.
  3. Error analysis: Hand-read the failures and group them into types.
  4. Adjust: Fix the biggest failure type with data, features, architecture or hyperparameters.

Exit: The eval metric hits the target, or improvements stall.

★ Karpathy's Recipe for Training Neural NetworksBecome one with the data → Skeleton + dumb baselines → Overfit → Regularize → Tune → Squeeze

Origin: Andrej Karpathy's 2019 blog post of the same name. For training a model by hand. The steps run from simple to complex, so each bug shows up early.

  1. Become one with the data: Spend hours looking at real examples. Find duplicates, label errors and patterns before writing any model code.
  2. Skeleton + dumb baselines: Build the full train/eval pipeline with a tiny model. Fix the random seed, visualize inputs right before they reach the model, and beat a trivial baseline.
  3. Overfit: Get a model big enough to drive training loss near zero. This proves the pipeline can learn.
  4. Regularize: Trade some training fit for validation performance with more data, augmentation, dropout, weight decay or early stopping.
  5. Tune: Search hyperparameters, preferring random search over grid search.
  6. Squeeze: Get the last gains from ensembles and training longer.

Exit: The validation metric hits its target.

Goodfellow's Practical MethodologySet goals → Build end-to-end fast → Instrument → Make one change → Repeat

Origin: The "Practical Methodology" chapter of Deep Learning by Ian Goodfellow, Yoshua Bengio and Aaron Courville (2016). For any applied ML project.

  1. Set goals: Choose the error metric and the target value, based on what the product needs.
  2. Build end-to-end fast: Get a working pipeline with a reasonable default model as early as possible.
  3. Instrument: Diagnose the bottleneck. Is it underfitting, overfitting, the data or a software bug?
  4. Make one change: Gather more data, change capacity, adjust hyperparameters or fix the bug, depending on what the diagnosis found.
  5. Repeat: Measure again and go back to step 3.

Exit: The metric hits the goal set in step 1.

Radford-style Scale loopPick a simple general objective → Scale → Probe → Repeat

Origin: A summary of Alec Radford's known approach across GPT, CLIP and Whisper. He hasn't published this as a loop. For foundation-model research.

  1. Pick a simple general objective: Choose a training task broad enough that solving it needs many skills, such as predicting the next token or matching images to captions.
  2. Scale: Add more data and more compute instead of a more complex architecture.
  3. Probe: Test for abilities the model wasn't trained for directly, such as zero-shot tasks.
  4. Repeat: Scale further in the direction where new abilities appeared.

Exit: New abilities stop appearing as you scale.

RLHFGenerate → Compare → Reward model → Optimize

Origin: Christiano et al. (2017), and OpenAI's InstructGPT (2022). For aligning a language model with what people actually want.

  1. Supervised fine-tune: Train the base model on example answers written by humans.
  2. Generate: The model writes several answers to each prompt.
  3. Compare: Humans rank which answers are better.
  4. Reward model: Train a model to predict those human rankings.
  5. Optimize: Update the language model to score higher on the reward model (for example with PPO), while keeping it close to the original model.
  6. Repeat: Collect fresh comparisons on the improved model.

Exit: Human preference win rate and safety evals hit their targets.

Active LearningTrain → Query → Label → Retrain

Origin: Classic machine learning. For projects where labeling data is expensive.

  1. Train: Fit a model on the small labeled set.
  2. Query: Pick the unlabeled examples the model is least sure about.
  3. Label: A human (or a stronger model) labels only those examples.
  4. Retrain: Add them to the training set and fit again.

Exit: Accuracy hits the target, or the labeling budget runs out.

Research

These three loops are built from the loops above. Run them in order: Deep Research gathers the knowledge, Hypothesis tests it and Tool Scout turns it into a decision. Kolb is for learning a subject yourself.

Deep ResearchFrame → Decompose → Search → Synthesize → Critique → Fill gaps → Record

Built from: Orchestrator → Workers, ReAct, Evaluator-Optimizer, Reflexion. For questions answered from the web or papers.

  1. Frame: Write the question in one sentence and what a good answer looks like.
  2. Decompose: The orchestrator splits the question into 3–6 sub-questions.
  3. Search (workers in parallel): Each worker takes one sub-question and loops Search → Read → Note until it has sources.
  4. Synthesize: Merge the findings into a draft answer, with a citation for every claim.
  5. Critique: A separate reviewer checks for gaps, contradictions, weak sources and claims with only one source.
  6. Fill gaps: Send the critic's list back to the workers.
  7. Record: Write a sources log and the open questions.

Exit: Every sub-question is backed by at least two good sources and the critic finds no major gaps. Stop after at most 3 rounds.

HypothesisObserve → Hypothesize → Predict → Experiment → Analyze → Ablate → Record

Built from: Scientific method, ML iteration, PDCA, Musk's "Delete" step. For technical research, such as ML experiments, performance and "does X work?"

  1. Observe: State what you saw that needs explaining.
  2. Hypothesize: Write one testable claim.
  3. Predict: Write down the result you expect before running anything.
  4. Experiment: Make the smallest test that could prove the claim wrong. Change one variable at a time.
  5. Analyze: Compare the actual result with your prediction and look at the failures by hand.
  6. Ablate: Remove parts to see which ones actually matter.
  7. Record: Log the hypothesis, result and decision so you never rerun the same experiment.

Exit: The hypothesis is confirmed or refuted and you've made a decision.

Tool ScoutQuestion → Scan → Shortlist → Spike → Debate → Record

Built from: Double Diamond, Best-of-N, Debate, Musk's "Question" step. For choosing a library, framework, model or vendor.

  1. Question: Define the must-have criteria and cut the nice-to-haves.
  2. Scan (diverge): List 5–10 options.
  3. Shortlist (converge): Keep 2–3 that meet every must-have.
  4. Spike: Build the same tiny prototype with each option.
  5. Debate: Make the strongest case for each option, then pick one.
  6. Record: Write a one-page decision note covering the choice, the reasons and what would make you switch.

Exit: One option is chosen and the decision note is written.

Kolb Learning CycleExperience → Reflect → Conceptualize → Experiment

Origin: David Kolb, Experiential Learning (1984). For learning a new skill or subject, such as a course or a new framework.

  1. Experience: Do something concrete, such as building a small model or running a tutorial.
  2. Reflect: Note what happened and what surprised you.
  3. Conceptualize: Connect it to the theory and explain it in your own words.
  4. Experiment: Apply the idea to a new problem, which becomes the next experience.

Exit: You can explain the concept and apply it unassisted to a problem you haven't seen.

Writing

Writing Process, Editor loop, Working Backwards and Critical Response Process are established methods. AI Slop Grader and Persuasion Grader are built from Evaluator-Optimizer and Debate. Run the Editor loop first, then the graders on the near-final draft.

Writing ProcessPlan → Draft → Review (recursive)

Origin: Linda Flower and John Hayes's cognitive process model of writing (1981), the basis of most writing teaching. For any piece of writing.

  1. Plan: Set the goal, the reader and the main point. Gather material and sketch an outline.
  2. Draft (translate): Turn the plan into sentences fast. Don't edit while drafting.
  3. Review: Reread against the goal, then revise.
  4. Recurse: Go back to whichever stage the review shows is weak. A muddy point means replanning, not polishing.

Exit: The draft does what the plan set out to do for that reader.

Editor loopDevelopmental → Line → Copy → Proof

Origin: The editing stages used in book and magazine publishing. For long or important pieces. Go big to small: never polish sentences in a section you might cut.

  1. Developmental edit (structure): Write a reverse outline, one line per paragraph. Check that the argument holds, the order is right and nothing is missing or repeated. Cut or move whole sections.
  2. Line edit (style): Tighten sentences, cut filler, fix rhythm and voice, and make every paragraph lead with its point.
  3. Copy edit (correctness): Check grammar, consistency, facts, names, numbers and links.
  4. Proofread: Do a final read in the finished format, ideally aloud or by a fresh reader.

Exit: A full pass at each level finds nothing worth changing.

Working Backwards (PR/FAQ)Press release → FAQ → Review meeting → Revise

Origin: Amazon. Write the launch press release before building anything. For product and project proposals.

  1. Press release: Write a one-page announcement in plain language, for the customer, as if the product already shipped.
  2. FAQ: Answer the hard questions, both customer and internal (cost, risks, why now).
  3. Review meeting: Readers silently read the doc, then critique it.
  4. Revise: Rewrite until the customer benefit is obvious and the hard questions have good answers. If it can't get there, kill the idea.

Exit: Reviewers agree it's worth building, or it's killed. Both are wins.

AI Slop GraderScore → Flag tells → Rewrite → Re-score

Built from: Evaluator-Optimizer. For any draft written or edited by AI, before a human reads it.

  1. Score (grader): Rate the draft 1–7, where 7 reads like a person who knows the subject wrote it.
  2. Flag tells: List each instance with its line. Look for:
    • Filler openers and closers ("In today's fast-paced world," "In conclusion")
    • Stock words ("delve," "tapestry," "leverage," "robust")
    • Automatic triplets and "not X, but Y" setups
    • Em-dash overload and hedging ("it's important to note")
    • Vague claims with no numbers or names
    • Every paragraph the same length and shape
  3. Rewrite (writer): Fix only the flagged lines. Use plain words, specifics and varied rhythm, and keep the meaning.
  4. Re-score: A fresh grader, one that didn't see the earlier draft, scores it again.

Exit: A score of 7, or at most 3 rounds. Fact-check after the last round, since rewrites can drift.

Persuasion GraderDefine the ask → Draft → Grade → Skeptic attack → Revise

Built from: Evaluator-Optimizer, Debate, and Aristotle's appeals (logic, credibility, emotion). For proposals, pitches, cover letters and sales emails.

  1. Define the ask: Name the one reader, the one action you want from them, and their main objection.
  2. Draft (writer): Write the piece.
  3. Grade (grader): Score 1–5 on each of these:
    • Clear ask
    • Reader's benefit stated in their terms
    • Evidence (numbers, examples, proof)
    • Credibility
    • Main objection handled
    • Easy next step
  4. Skeptic attack (opponent): A second agent plays the doubtful reader and writes the reasons they'd say no.
  5. Revise: Fix the lowest-scoring criterion and answer the skeptic's strongest objection.

Exit: Every criterion scores 4 or higher and the skeptic has no unanswered objection. Stop after at most 3 rounds.

Critical Response ProcessMeaning → Writer's questions → Neutral questions → Opinions

Origin: Liz Lerman's feedback method, widely used in writing workshops. For getting feedback from people (or agents) without derailing the writer.

  1. Statements of meaning: Readers say what struck them and what worked.
  2. Writer's questions: The writer asks about the specific parts they're unsure of.
  3. Neutral questions: Readers ask questions without hidden opinions ("What's the goal of the opening?" rather than "Why is the opening so slow?").
  4. Opinions, with permission: Readers offer opinions only if the writer agrees to hear them.
  5. Revise: The writer decides which feedback to use.

Exit: The writer has a revision plan. Run another round on the next draft.

Rules for every loop

  1. Define "done" before starting. If you cannot test it, you cannot loop on it.
  2. Grade with a verifier, not a vibe. Use tests, linters, metrics or a written rubric.
  3. Separate the builder from the reviewer. A reviewer with fresh context catches what the author cannot.
  4. Cap the number of iterations. Set a round limit and an escalation path for when it is hit.
  5. Write lessons to a file. Reflections, root causes and postmortems keep the loop from repeating mistakes.
  6. Keep each turn small. Short loops give feedback faster than one long pass.
  7. Diverge, then converge. Generate options before committing to one.
  8. Hand off in writing. Every loop ends with a next-steps note the next loop or person can start from.
  9. Lock in wins. Turn a fix into a test, check or template so it stays fixed.
